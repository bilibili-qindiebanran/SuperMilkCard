# 双模式联网语音角色与智能家居实施计划

> 交接目标：在 `live2dESP32` 分支实现 ESP32 的联网、配网、双模式语音互动，并可修改 `ESP32/`、`Windows/` 及其全部 Live2D 网页工程。首期完成“Live2D 局域网联动模式”和“独立角色 API 模式”；米家智能家居只进入受控调研与架构预留阶段，未经官方能力、授权方式和安全评审确认不得接入真实账号。

## 0. 已确认的产品决策

- ESP32 不原生运行 Cubism Live2D；Windows 网页端继续运行完整 Live2D。
- ESP32 的互动形象使用 LVGL 图元绘制的 Emoji 风格表情，不导入预渲染 Live2D 图集。
- 配网 SoftAP 固定为 `SuperMilkCard`，无密码；仅用于首次/故障配网，设备必须在屏幕上明确提示当前为开放热点。
- 不使用 ESP32 与 Windows 之间的共享令牌；LLM、STT、TTS 等 API Key 不得经 TCP 下发给 ESP32。
- “返回桌面”指返回 ESP32 主页。
- 本计划允许修改所有项目文件；所有改动均在独立 `live2dESP32` 分支完成。

## 1. 范围、非目标与完成定义

### 1.1 首期范围

1. ESP32 Wi-Fi STA、SoftAP 配网、网络状态显示与持久化配置。
2. 由实体按键和触摸共同操作的“语音互动模式选择”页面。
3. **Live2D 局域网联动模式**：ESP32 采集语音，传给同一局域网内已运行的 Windows 网页 Live2D；Windows 负责 STT、LLM、Live2D 情绪/动作、TTS，ESP32 显示同步 Emoji 表情、文本摘要并播放音频。
4. **独立角色 API 模式**：未连接 Windows Live2D 时，ESP32 根据设备已配置的 OpenAI 兼容 API 与角色提示词，独立完成 STT → 对话 → TTS（TTS 可按配置关闭）。
5. 从 Windows 网页 Live2D 导出当前角色提示词和基础角色资料，并通过局域网一次性导入 ESP32 的独立角色配置。
6. 为未来智能家居能力预留“工具调用/设备能力”抽象和米家调研门禁。

### 1.2 非目标

- 不在 ESP32 上运行 Cubism、WebGL、PIXI 或完整 Live2D 模型。
- 不做公网远程控制、端口映射或默认云端中转。
- 不通过抓包、逆向、模拟网页登录或复用个人 Cookie 的方式连接米家账号。
- 首期不实现家电控制；只完成官方支持情况、账号授权方式与安全边界的验证记录。
- 不将 Windows 的 LLM/TTS/STT API Key 复制到 ESP32。

### 1.3 首期完成定义

- 新设备可自行配网；用户可进入模式选择页并用触摸或实体按键选择模式。
- Windows Live2D 在线时，ESP32 语音输入可驱动 Windows 对话和 Live2D，同时收到回复音频、文本摘要与表情状态。
- Windows Live2D 不在线时，用户可选择独立角色 API 模式进行语音对话；角色提示词可从 Windows 导入。
- 任一路径失败都显示可理解状态、提供返回和重试，不重启设备也可恢复。

## 2. 用户流程与模式状态机

### 2.1 入口与按键规范

在 ESP32 主页增加“语音互动”入口；进入后展示两个模式卡片：

| 模式 | 入口文案 | 适用条件 | 主要责任方 |
| --- | --- | --- | --- |
| Live2D 联动 | `连接电脑 Live2D` | 同一局域网内发现并握手成功 | Windows |
| 独立角色 | `独立角色对话` | ESP32 已连接 Wi-Fi，且直接 API 配置通过校验 | ESP32 + 云端 API |

实体按键沿用当前硬件定义：GPIO38 为“返回/上一项”，GPIO4 为“确认/下一项”。触摸操作必须与实体按键完成同一流程：

1. 进入模式选择页时默认聚焦 `连接电脑 Live2D`，并用现有 Fluent 2 主色高亮焦点。
2. GPIO38 **短按**：在两个模式卡片之间切换焦点；触摸卡片：直接切换焦点。
3. GPIO4 **短按**：执行当前焦点模式的预检和连接；触摸“进入”执行同一行为。
4. GPIO38 **长按**：从模式选择页返回 ESP32 主页；从任一互动子状态取消录音/播放/请求并返回模式选择页。互动页左上角始终提供“返回桌面”。

> 实施的第一个 UI 子任务是为 `board_keys` 增加可靠的长按事件（建议阈值 800 ms），并在模式选择页显示“返回：切换 / 确认：进入 / 长按返回：桌面”的操作提示。不要依赖当前 LVGL 的默认焦点导航来猜测实体按键语义。

### 2.2 模式选择与回退规则

为避免在用户无感知时消耗云端 API 或泄露语音，**不自动从 Live2D 模式切到独立 API 模式**。规则如下：

1. 用户选择 `连接电脑 Live2D` 后，ESP32 在最多 5 秒内执行发现/连接/握手。
2. 成功：进入 Live2D 联动页，发布 `linked` 状态。
3. 失败：留在错误页，展示失败原因、`重试` 与 `切换到独立角色` 两个明确操作；仅用户确认后才进入独立模式。
4. 用户选择 `独立角色对话` 后，先检查 Wi-Fi、API 端点、必需 Key、角色提示词是否有效；通过才录音。
5. 独立模式运行中 Windows Live2D 恢复在线，不自动抢占会话；仅在用户返回模式选择页时更新在线状态。
6. 所有网络中断都停止录音/上传、取消进行中的请求，并保留最后一条安全截断的显示文本。

### 2.3 会话状态

```text
DESKTOP
  -> MODE_SELECT
      -> LINK_CHECKING -> LINKED_IDLE -> LINKED_LISTENING -> LINKED_WAITING -> LINKED_SPEAKING
      -> DIRECT_CHECKING -> DIRECT_IDLE -> DIRECT_LISTENING -> DIRECT_STT -> DIRECT_LLM -> DIRECT_TTS
  -> ERROR / PROVISIONING
```

- 每次状态迁移都通过单一 `app_state` 快照发布；网络、音频任务不得直接改 LVGL 对象。
- `BACK` 从任意互动子状态终止录音/播放/HTTP 请求并回到 `MODE_SELECT`；从选择页回到 `DESKTOP`。
- 互动页隐藏底部导航，恢复桌面后恢复普通导航和刷新策略。

## 3. 总体架构

```text
                             ┌────────────────────────────┐
ESP32-S3                     │ Windows Electron / 网页端  │
┌───────────────────────┐    │ Live2D + STT + LLM + TTS   │
│ LVGL Emoji 互动 UI     │◄──►│ 局域网桥接服务 / 协议适配器 │
│ I2S 麦克风 / 扬声器    │ TCP│ 角色资料导出服务           │
│ Wi-Fi / 配网页 / NVS   │    └────────────────────────────┘
│ Direct API 客户端      │
└───────────┬───────────┘
            │ HTTPS（仅独立模式）
            ▼
      OpenAI 兼容 STT / LLM / TTS 服务
```

### 3.1 职责边界

| 模块 | Live2D 联动模式 | 独立角色 API 模式 |
| --- | --- | --- |
| ESP32 | 录音、发送 PCM、显示状态/摘要/Emoji、播放 Windows 下发音频 | 录音、HTTPS 调用、显示状态/摘要/Emoji、播放 TTS 音频 |
| Windows | STT、LLM、Live2D 表情动作、TTS、会话上下文、角色导出 | 可选：仅提供角色资料导出与设置编辑，不参与实时对话 |
| 云端 API | 由 Windows 统一访问 | 由 ESP32 直接访问已配置端点 |

### 3.2 性能边界

- Emoji 以 LVGL 的圆形、弧线、线条和文本绘制，不依赖彩色 Unicode Emoji 字体，也不加载 Live2D 位图资源。
- 表情枚举固定为 `neutral`、`happy`、`sad`、`angry`、`surprised`、`thinking`；动作固定为 `idle`、`listening`、`speaking`、`thinking`。
- 动效仅做 2–8 FPS 的眨眼/嘴型/呼吸；无状态变化时不得全屏持续刷新。
- 语音缓冲采用固定大小环形缓冲和流式分片，禁止整段长录音、整段 TTS 音频无限制常驻 PSRAM。

## 4. ESP32 实施计划

### A. 网络、配置与安全

建议新增：`ESP32/src/network/`、`ESP32/src/config/`、`ESP32/src/protocol/`。

1. **Wi-Fi 管理器**
   - STA 自动重连、RSSI/IP/SSID 状态、失败退避、网络事件队列。
   - 首次启动、连续连接失败或设置页点击时，开启 SoftAP：SSID `SuperMilkCard`、无密码。
   - 开放热点只用于配网：进入后屏幕显著显示“开放配网热点”，并限制服务仅监听 AP/本地网卡；保存成功或超时后关闭。

2. **配网页**
   - 使用 ESP-IDF HTTP Server 和内嵌静态页面，不增加大型 Web 依赖。
   - 配置 Wi-Fi、Windows 发现/手动地址、独立模式 LLM/STT/TTS 的 Base URL/模型/开关、角色选择与设备名。
   - API Key 输入必须为 password 字段，页面读取配置时只能返回 `hasApiKey`，不得回传明文。
   - 提供保存并连接、测试连接、重新扫描、忘记 Wi-Fi、清除独立 API Key 和恢复网络设置。

3. **凭据存储**
   - Wi-Fi 密码与独立模式 API Key 使用独立 NVS 命名空间，日志绝不输出明文。
   - 先验证目标板可用的 NVS 加密/Flash 加密配置；若实际烧录流程不支持，独立 API 模式页面必须明确提示“设备本地保存 Key 的风险”，并要求用户二次确认。
   - 不持久化音频原始数据、转写全文或完整聊天记录；仅保留用户明确需要的角色配置和短会话内存上下文。

### B. 发现、连接与局域网桥接

1. **连接策略**
   - 首选 mDNS 广播/发现：Windows 发布 `_supermilkcard._tcp` 服务，TXT 包含协议版本、设备名称、TCP 端口和能力位。
   - 兜底手动配置 Windows IP/端口；当 mDNS 不可用时仍可连接。
   - 保留设备 ID 握手、协议版本和能力协商；无共享令牌时仅允许同一受信任局域网使用，Windows UI 提示这一限制。

2. **协议统一**
   - 将 `ESP32/接口文档.md` 扩展为单一事实来源；协议版本升级为可协商版本，拒绝不兼容客户端。
   - 沿用现有 `AA 55` 帧头和 HELLO/TEXT/AUDIO 分帧，新增 `session_id`、`request_id` 防止重连后旧音频/旧回复串入新会话。
   - 新增消息：

```json
{ "type": "capabilities", "protocol": 2, "modes": ["live2d_link", "direct_api"], "audio": { "pcm": [16000, 1, 16] } }
```

```json
{ "type": "mode_event", "mode": "live2d_link", "state": "listening", "sessionId": "..." }
```

```json
{ "type": "live2d_state", "expression": "happy", "motion": "speaking", "messagePreview": "今天也要元气满满哦！", "sessionId": "..." }
```

```json
{ "type": "voice_start", "requestId": "...", "format": "pcm", "sampleRate": 16000, "channels": 1, "bits": 16 }
```

```json
{ "type": "voice_end", "requestId": "..." }
```

   - 所有 JSON 必须设总长度、字段白名单、UTF-8 检查和超时；任何未知/过大帧均丢弃并上报简短错误。

3. **Windows 音频联动**
   - ESP32 在按住/点击录音后发送 `voice_start` + 分片 PCM + `voice_end`。
   - Windows 复用现有 STT、聊天、Live2D、TTS 服务：转写进入同一聊天会话，驱动网页 Live2D，回复文本和状态推给 ESP32，TTS 音频使用流式分片下发。
   - Windows 断线时 ESP32 立即停止发送、退出录音态并提示“电脑 Live2D 已断开”。

### C. 独立角色 API 模式

1. **API 配置模型**
   - 在 ESP32 端单独定义 `DirectApiConfig`：`llm`、`stt`、`tts` 三组 `enabled/baseUrl/model/hasApiKey` 与必要参数；不要复用或同步 Windows 私密配置。
   - 首期只支持 HTTPS 的 OpenAI 兼容端点：`/v1/audio/transcriptions`、`/v1/chat/completions`、`/v1/audio/speech`。任何非 HTTPS 端点必须在 UI 显著警告并默认拒绝。
   - LLM 首期使用非流式短回复以降低 ESP32 JSON/连接管理复杂度；第二阶段再评估 SSE 流式输出。

2. **语音链路**
   - 采集 I2S 麦克风为 16 kHz、单声道、16-bit PCM；设置最大录音时长、静音检测和用户主动取消。
   - 以流式/临时文件方式封装为 WAV 后上传 STT；严格设置正文上限、HTTP 超时、取消令牌与错误分类。
   - 转写文本拼接角色系统提示词、有限窗口的本轮上下文，发送 LLM。
   - LLM 文本去除任何内部控制标签后显示；由情绪解析映射 Emoji；若配置 TTS 则请求音频并边收边播或受限缓存播放。

3. **角色与提示词**
   - ESP32 本地角色记录只包含 `id`、`name`、`avatarStyle`、`systemPrompt`、`defaultExpression`、`version`，并设置提示词字节上限。
   - 本地新建/编辑角色仅在配网页或设置页完成；完整提示词不在普通互动页展示。
   - 默认没有角色时禁用独立模式的进入按钮，并引导导入或创建。

### D. UI 与状态模型

1. 新建页面：`ui_page_voice_mode`、`ui_page_live2d_link`、`ui_page_direct_chat`、`ui_page_network`；按现有 `ui_theme.*` 保持 Fluent 2 风格。
2. 扩展 `app_state`：
   - `network`：Wi-Fi、IP、RSSI、配网状态。
   - `bridge`：发现结果、Windows 连接、协议版本、最近错误。
   - `session`：当前模式、状态、`session_id`、录音/播放状态、文本摘要、表情/动作。
   - `direct_api`：配置完整性、可用服务、最近错误；绝不含 API Key。
3. 设置页新增“网络与配网”“电脑 Live2D”“独立角色 API”“角色资料”入口；互动页面只展示必要控制、状态与返回桌面。

## 5. Windows / 网页 Live2D 实施计划

### A. 局域网桥接服务

1. 现有 `Windows/src/main/services/esp32.ts` 是 Windows 作为 TCP 客户端的实现。改造时优先评估两种兼容方案：
   - 方案一（推荐）：Windows 保留客户端行为，ESP32 开启 TCP 服务端；通过 mDNS 发布 ESP32 地址，Windows 自动连接。
   - 方案二：Windows 新增 TCP 服务端，ESP32 作为客户端；仅在 ESP32 NAT/发现能力或网络重连可靠性评估证明更优时采用。
2. 在协议 v2 中统一一个方向，删除双向连接竞争。必须记录选择理由并更新 `ESP32/接口文档.md`、Windows 类型、Preload、IPC 和 ESP32 端实现。
3. 增加会话管理、音频流转发、连接状态事件、流量/长度限制与断线清理。

### B. Live2D 与聊天联动

1. 为 ESP32 设备会话增加独立 chat session，不污染桌面手工聊天历史；可在 Windows UI 中查看/清空该会话。
2. ESP32 语音转写成功后，调用现有聊天 store/LLM 服务；沿用现有情绪/动作标签解析和 Live2D controller。
3. 把归一化的 `expression`、`motion`、回复摘要发送到 ESP32；其值必须经过白名单映射。
4. 将最终回复送入现有 TTS 服务，按协议分片发送给 ESP32；Windows TTS 失败时仍发送文字和 Live2D 状态。
5. 不强制抢占 Windows 窗口焦点或桌面语音播放；Windows 设置中新增“ESP32 会话是否同时在电脑扬声器播放”的显式开关，默认关闭。

### C. 角色资料导出/导入

1. 在 Windows 设置页的 Live2D/人格区域新增“导出到 ESP32”按钮，导出当前 `persona.systemPrompt`、名称、默认表情、模型/角色显示名和版本。
2. 通过**已建立的同一局域网 TCP 连接**发送 `persona_export` 控制帧；不走开放 HTTP 下载，也不包含 Windows API Key、模型文件或 Live2D 纹理。
3. ESP32 展示确认页（角色名称、提示词长度、来源设备），用户确认后写入 NVS；支持覆盖、新建副本、取消。
4. 导入后 ESP32 在独立模式使用该系统提示词。提示词的 Live2D 专用标签应由 Windows 在导出前转换/剥离，保留可被 Emoji 映射的通用情绪指令。

## 6. 米家智能家居：仅调研与架构预留

### 6.1 必须先完成的调研门禁

实施 Agent 在开始任何账号绑定代码前，必须输出 `ESP32/docs/米家智能家居接入调研.md`，并满足以下全部问题：

1. 小米/米家是否提供面向本项目、地区和个人/开发者身份可用的**官方**账号授权、设备列表和设备控制 API。
2. 官方授权流程是否支持 OAuth/OIDC、授权码回调、令牌刷新、撤销授权和最小权限。
3. 所需开发者资质、审核、设备/产品绑定、地区限制、速率限制、隐私政策和用户授权页要求。
4. 可控设备类别、能力模型、命令确认/回执、离线设备处理和审计日志要求。
5. 密钥与刷新令牌能否安全保存在 Windows；若只能存 ESP32，是否具备 Flash/NVS 加密与物理攻击风险说明。
6. 结论和证据只允许引用官方开发者文档、官方 SDK、官方协议站点或书面开发者支持回复；没有官方可用路径即停止，不采用非官方逆向协议。

### 6.2 架构预留（不连接真实账号）

在 Windows 端建立厂商无关接口，ESP32 不直接持有智能家居账号令牌：

```ts
interface SmartHomeProvider {
  getAuthorizationStatus(): Promise<'unconfigured' | 'authorized' | 'expired'>
  listDevices(): Promise<SmartHomeDevice[]>
  execute(command: SmartHomeCommand): Promise<SmartHomeCommandResult>
  revokeAuthorization(): Promise<void>
}
```

- 首期只实现 `MockSmartHomeProvider`，用于 UI 和角色工具调用测试；不发出真实家电命令。
- 真实厂商 Provider（包括米家）只在完成第 6.1 节后新建，并将 OAuth 回调、令牌刷新、审计日志和确认机制放在 Windows 主进程。
- LLM 不可直接执行家电命令：必须采用“LLM 提议 → Windows 展示目标设备与动作 → 用户确认 → Provider 执行 → 回执展示”的闭环。
- 高风险动作（门锁、安防、燃气、加热等）默认不支持，除非后续单独完成威胁建模、设备白名单和更强确认机制。

## 7. 测试与验收

### 7.1 自动化与静态验证

- Windows：`npm run typecheck`、`npm run lint`、相关主进程/协议单元测试。
- ESP32：`pio run -d ESP32`；对帧编解码、JSON 白名单、状态机、NVS 配置迁移和超时逻辑添加可脱机测试。
- 任何协议字段变更同步更新 `ESP32/接口文档.md`，并为 v1/v2 不兼容行为提供明确错误。

### 7.2 真机验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 首次启动 | 自动开启 `SuperMilkCard` 无密码热点，可在网页完成 Wi-Fi 配置 |
| Live2D 在线 | 5 秒内握手；录音可驱动 Windows Live2D；ESP32 收到文字、Emoji 状态和语音 |
| Live2D 离线 | 明确提示失败；只有用户选择后才进入独立 API 模式 |
| 独立模式 | STT、LLM、TTS 任一失败均可显示具体错误、取消/重试并返回 |
| 模式切换 | 不串音、不使用旧 session 的回复、不遗留录音/播放任务 |
| 网络中断恢复 | 停止上传并恢复到可重试状态；恢复后无需重启设备 |
| 角色导入 | Windows 不传 API Key/模型资源；ESP32 确认后才保存提示词 |
| 安全 | 日志、设置回读、协议包和页面均不包含 Wi-Fi 密码/API Key |
| 稳定性 | 两种模式分别连续运行 2 小时，无 WDT、内存持续增长或死连 |

### 7.3 性能目标

- 按键/触摸进入或返回页面：≤ 150 ms 可见反馈。
- 局域网 Live2D 状态到 Emoji 可见延迟：≤ 300 ms（正常 RSSI 条件）。
- 首次模式连通预检：≤ 5 s；失败后 ≤ 1 s 展示可操作错误。
- 独立模式的端到端语音延迟仅记录实测，不作未验证的固定承诺；必须记录 STT、LLM、TTS 三段耗时。

## 8. 分阶段执行顺序与提交建议

1. `docs`: 将本计划和现有接口文档对齐；确认 TCP 连接方向与 mDNS 策略。
2. `feat(esp-net)`: Wi-Fi、NVS、SoftAP、HTTP 配网页、网络设置 UI。
3. `feat(protocol)`: 协议 v2、服务发现、握手、session/request ID、帧测试。
4. `feat(esp-ui)`: 模式选择、实体按键交互、Live2D 联动/独立模式页面、Emoji renderer、状态机。
5. `feat(windows-bridge)`: Windows 桥接会话、ESP32 音频输入、Live2D/聊天/TTS 下行。
6. `feat(direct-api)`: ESP32 HTTPS STT/LLM/TTS、配置模型、角色内存上下文、失败处理。
7. `feat(persona-transfer)`: Windows 导出、ESP32 确认导入、提示词转换与版本管理。

9. `test`: 完成第 7 节的构建、协议测试、真机矩阵和两小时稳定性记录。
